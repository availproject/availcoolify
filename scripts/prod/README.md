# Release pipeline

`.github/workflows/release.yml` tests, builds, pushes and deploys AvailCoolify. It replaces
`avail-production.yml`. It lives in `availproject/availcoolify` (a public repository) and deploys from the
`avail` branch.

No secret lives in GitHub. The jobs sign in to AWS with GitHub's OIDC token and read their secrets from
SSM Parameter Store. They reach the VMs through Teleport (a Machine ID bot). Neither CI nor people use SSH
keys: `sshd` stays on the VMs only for Coolify, which manages its servers over SSH.

## SSH: only between the VMs

| Who | How | SSH key |
| --- | --- | --- |
| CI (this workflow) | Teleport, as the bot `availcoolify-ci` | none |
| People | Teleport (`tsh ssh`) | none |
| People, when Teleport is down | SSH as root, after opening 58122 for your IP in the provider firewall | the break-glass key (`PROD_BREAKGLASS_SSH_PUBKEY`); its private half stays offline |
| Coolify, on the control plane, to its own host | SSH to `host.docker.internal` over the Docker bridge | its "localhost's key", generated by `bootstrap-host.sh` |
| Coolify, control plane to each app server | SSH on port 58122 | `avail-workers`, which Coolify makes on the first deploy (`worker-key.php`); the pipeline installs its public half |

What the pipeline enforces on every VM:

- **Provisioning stops if the VM is not in Teleport** (the `teleport` service must be running). Nothing is
  changed first, so a typo in a node name cannot lock anyone out.
- `sshd` listens on the one Coolify port only; port 22 is closed. Key-only, no passwords.
- The only keys in root's `authorized_keys` are Coolify's and the break-glass key (`PROD_BREAKGLASS_SSH_PUBKEY`; while
  that variable is unset, the break-glass key is removed like any other). Anything else (a key the provider injected when the VM was
  created, someone's laptop key) is listed by fingerprint, backed up next to the file, and removed.
- Network: the provider firewall keeps SSH off the internet. On the **control plane** the port can stay closed
  entirely, because Coolify reaches its own host over the Docker bridge. On **app servers** it is open to the
  control plane's IP only.

| Trigger | What runs |
| --- | --- |
| Pull request to `avail` (`test.yml`) | Test suite minus `tests/avail-ci-skip.txt`, then shellcheck, `php -l`, actionlint and `alloy fmt`. No AWS, no secrets. Branch protection on `avail` requires it; fork runs by outside contributors wait for a maintainer's approval |
| Push to `avail` (`release.yml`) | Build `docker/production/Dockerfile` (no tests: the pull request already passed them) and push `registry.digitalocean.com/availj/availcoolify:custom-<sha9>` (label `coolify.managed=true`) |
| Manual: **deploy** | Build HEAD, pull it on the control plane, `deploy-custom.sh`, configure the instance, log collector, smoke checks, Slack |
| Manual: **provision** | From enrolled but bare VMs: Docker, SSH for Coolify, `/data/coolify` and `.env`, then everything in deploy |
| Manual: **rollback** | Redeploy an earlier image (`image_tag`, for example `custom-06e5e21b9`). Compose files and `deploy-custom.sh` come from the commit that image was built from |

`deploy`, `provision` and `rollback` run in the GitHub environment **production**, which requires a reviewer's
approval. A push to `avail` only builds the image; production changes only through a manual run.

```
push to avail ─▶ image job ──OIDC──▶ AWS build role ──▶ SSM: DOCR_PUSH_TOKEN ─▶ push to DigitalOcean registry
                                  approval (environment: production)
                                          │
release job ──OIDC──▶ AWS release role ──▶ SSM: every secret under the prefix
            ──OIDC──▶ Teleport bot ──▶ control plane / app servers: files, deploy-release.sh, log collector
                                          └▶ control plane pulls the image with the read-only registry token
```

## One-time setup

### 1. AWS

Create the GitHub OIDC identity provider (`token.actions.githubusercontent.com`, audience `sts.amazonaws.com`),
then two roles. Two, because the build runs on every push to `avail` without an approval: its role must only be
able to read the registry push token. The role that reads every secret is trusted for the `production`
environment only, so it sits behind the approval.

**Release role** (`AWS_ROLE_ARN`). Trust policy:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:availproject@125018949/availcoolify@1379972354:environment:production"
      }
    }
  }]
}
```

Permissions:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["ssm:GetParametersByPath", "ssm:GetParameter"],
    "Resource": [
      "arn:aws:ssm:<REGION>:<ACCOUNT_ID>:parameter/avail/coolify/prod",
      "arn:aws:ssm:<REGION>:<ACCOUNT_ID>:parameter/avail/coolify/prod/*"
    ]
  }]
}
```

**Build role** (`AWS_BUILD_ROLE_ARN`). Same trust policy, but `sub` is `repo:availproject@125018949/availcoolify@1379972354:ref:refs/heads/avail`.

This repository uses GitHub's *immutable* OIDC subject (owner and repository ids, not names), so the name-only form
`repo:availproject/availcoolify:…` is rejected. Check the prefix with
`gh api repos/availproject/availcoolify/actions/oidc/customization/sub` (`sub_claim_prefix`).
Permissions: `ssm:GetParameter` on `.../parameter/avail/coolify/prod/DOCR_PUSH_TOKEN` only.

If the parameters use a customer-managed KMS key instead of `alias/aws/ssm`, both roles also need `kms:Decrypt`
on that key. Pull requests never get an AWS role: their OIDC subject is not trusted.

Then create the SecureString parameters (next section) under one prefix, `/avail/coolify/prod/` by default.

### 2. Teleport

Both VMs enrolled as nodes (`teleport` service active) with the label `project: availcoolify`, the same
`project` label every node in the cluster carries (the `nexus-v2-ssh` role matches `project: nexus-v2`). Node
names follow the cluster's `<name>-NN-<region>` style, e.g. `availcoolify-cp-01-fra1`. Then, on the cluster (commands follow Teleport's GitHub Actions guide; check them against
your cluster's version):

```yaml
# ci-role.yaml
kind: role
version: v7
metadata:
  name: availcoolify-ci
spec:
  allow:
    logins: [root]
    node_labels:
      project: availcoolify
---
# ci-token.yaml
kind: token
version: v2
metadata:
  name: availcoolify-ci
spec:
  roles: [Bot]
  join_method: github
  bot_name: availcoolify-ci
  github:
    allow:
      - repository: availproject/availcoolify
        environment: production
        ref: refs/heads/avail
```

```bash
tctl create -f ci-role.yaml
tctl bots add availcoolify-ci --roles=availcoolify-ci   # the one-time token it prints is not used
tctl create -f ci-token.yaml
```

`TELEPORT_BOT_TOKEN` is the name of that join token (`availcoolify-ci`), not the bot.

### 3. DigitalOcean registry

Registry `availj` (`registry.digitalocean.com/availj`). Two API tokens, both scoped to the registry only:
one with write access (SSM `DOCR_PUSH_TOKEN`, used by the build) and one read-only (SSM `DOCR_TOKEN`, used by the
control plane to pull). DigitalOcean takes the token as both user name and password. Every push adds a tag;
delete old tags by hand, but keep the ones you may roll back to, and check the plan's storage limit.

### 4. GitHub

All of this needs a repository admin of `availproject/availcoolify`.

- Settings → Secrets and variables → Actions → **Variables** (repository level, because the build job has no
  environment). They are not secret; the table below lists them.
- Settings → Environments → `production`: add **required reviewers**, and under *Deployment branches and
  tags* choose **Selected branches → `avail`**. The repository is public and anyone with write access can start
  a workflow from any branch; this keeps the production jobs on `avail`. (The AWS build role and the Teleport
  token above only accept `avail` as well.)
- Settings → Actions → General: if the organisation limits which actions may run, allow
  `aws-actions/*`, `teleport-actions/setup`, `docker/*` and `shivammathur/setup-php`. The rest are GitHub's own.

**Because the repository is public:** run logs are public too. Secrets are masked and so is the AWS account id,
but the Teleport proxy address, node names, image tags and the dashboard URL are not secret and appear in the logs
and the run summary. Pull requests from forks run only the `test` job with no secrets, and the AWS roles do not
trust `pull_request` tokens, so they cannot reach AWS or Teleport. The workflow does not use `pull_request_target`.

| Variable | Example / default | Used by |
| --- | --- | --- |
| `AWS_BUILD_ROLE_ARN` | `arn:aws:iam::123456789012:role/avail-coolify-build` | build. While unset, pushes run the tests only |
| `AWS_ROLE_ARN` | `arn:aws:iam::123456789012:role/avail-coolify-release` | release |
| `AWS_REGION` | `eu-central-1` | both |
| `TELEPORT_PROXY` | `teleport.example.com:443` | release |
| `TELEPORT_BOT_TOKEN` | `availcoolify-ci` | release |
| `PROD_CONTROL_PLANE_NODE` | Teleport node name of the control plane | release |
| `PROD_APP_SERVER_NODES` | space-separated node names of the app servers | provision, log collector |
| `PROD_DASHBOARD_URL` | `https://deploy.example.com` | smoke checks, Coolify instance URL |
| `PROD_APPS_WILDCARD` | `https://apps.example.com` | default wildcard for new apps |
| `PROD_ROOT_USER_EMAIL` | `owner@example.com` | provision: first admin; their first Clerk login becomes the owner |
| `PROD_SSH_PORT` | default `58122` | the port Coolify uses |
| `PROD_AUTO_JOIN_DOMAINS` | default `availproject.org` | provision |
| `PROD_DB_SSLMODE` | default `require` | provision: used only when `DATABASE_URL` has no `sslmode` |
| `PROD_BREAKGLASS_SSH_PUBKEY` | `ssh-ed25519 AAAA… avail-breakinglass` (a public key, not a secret) | provision, deploy: kept in root's `authorized_keys` on every VM next to Coolify's key |

### 5. Provider (not automated)

Firewall: 80/443 open to the internet; SSH (58122) closed on the control plane and open to the control plane's
IP only on the app servers; 8000, 6001, 6002, 5432 and 6379 closed (Docker-published ports bypass `ufw`, so
this has to be the provider firewall). Managed Postgres 15+ with the control plane allowlisted and
point-in-time recovery on. On Postgres 15+ the app user cannot create tables in `public` by default; run once as the admin user, connected to the app database: `GRANT USAGE, CREATE ON SCHEMA public TO coolify;` (without it migrations fail with "permission denied for schema public"). Create the VMs without a personal SSH key if the provider lets you; if one was
injected, the pipeline removes it. Teleport is the way in, so test the provider's web console once for recovery.

### 6. Cloudflare (once, by hand)

The workflow holds no Cloudflare token and changes nothing there (decided 2026-10-09). Set this up once in the
zone, before the first provision of the real VMs:

| What | Setting |
| --- | --- |
| DNS | `A` `<dashboard host>` → control plane public IP, and `A` `*.<apps host>` → app server public IP, both **proxied**. The wildcard covers every app URL and PR preview, so no app ever needs its own record |
| TLS | A Configuration Rule for those two host names only: SSL **Full (strict)**. Leave the zone-wide setting alone. Two-level names (`x.apps.…`, PR previews) need Total TLS, i.e. Advanced Certificate Manager |
| Cache | A Cache Rule on the dashboard host, **bypass** for `/livewire/*`, `/app`, `/app/*`, `/auth/*`, `/webhooks/*`, `/preview-guard/*` |
| Rate limit | One rule on the dashboard host for `/auth/*` and `/webhooks/*`: 40 requests per 10 s per IP and colo, block for 10 s |

Custom app domains on other zones get their record from whoever owns that zone; Coolify shows what to add. The
deploy step still makes Traefik trust Cloudflare's IP ranges (`AVAIL_TRUST_CLOUDFLARE`), because the records
are proxied.

### 7. First run

0. Merge `feature/release-ci` into `avail` once it is reviewed and the settings above exist. **Run workflow** only works for a
   workflow that is on the default branch (`avail`), and the AWS build role, the Teleport token and the `production`
   environment all accept `avail` only, so the pipeline cannot be tried from the feature branch.
1. Create the two DNS records (setup step 6), then run **provision** and approve it. The smoke checks go through DNS and
   Cloudflare, so the records must exist first.
2. Sign in once with `PROD_ROOT_USER_EMAIL`.
3. App servers, without anyone touching a key: every deploy runs `worker-key.php` in the container, which makes Coolify's
   key `avail-workers` (ed25519, team 0) the first time and returns the same key after that. The pipeline installs its public
   half on every app server over Teleport and removes all other keys; the private half never leaves the control plane.
   Then Servers → Add (user `root`, port 58122, key `avail-workers`, the app server's private VPC address) and set the wildcard
   domain. To rotate the key, rename `avail-workers` in Keys & Tokens and run **deploy**: a new key is made and installed, the
   old one is removed from the app servers; switch the servers to the new key in the UI.
4. Add the GitHub App as a source, then run `php artisan avail:github-platform <id>` in the container.

## SSM parameters

Each is a SecureString under the prefix; the last path segment is the variable name.

| Parameter | Needed by | Notes |
| --- | --- | --- |
| `DOCR_PUSH_TOKEN` | build | registry token with write access |
| `DOCR_TOKEN` | deploy, provision, rollback | read-only registry token for the control plane |
| `DATABASE_URL` | provision | `postgres://user:pass@host:port/coolify?sslmode=require`. Percent-encode special characters in the password (`@` is `%40`) |
| `CLERK_CLIENT_ID`, `CLERK_CLIENT_SECRET`, `CLERK_BASE_URL` | provision (required), deploy (applied if present) | Clerk OAuth app. The base URL is required since 4.4.0 |
| `SLACK_WEBHOOK_URL` | optional | deploy results go to this channel |
| `CF_EMAIL_TOKEN` | optional | Cloudflare **account** API token with only *Email Sending: Edit*, IP-restricted to the control plane's public IP. Deploys turn on Coolify's transactional email over Cloudflare's SMTP (`smtp.mx.cloudflare.net:465`, TLS, user `api_token`), sent as `noreply@notify.avail.so`. The sending subdomain `notify.avail.so` is set up once in Cloudflare Email Sending |
| `SIGNOZ_OTLP_ENDPOINT` | optional | e.g. `https://otel2.avail.so` (no ingestion key); without it no log and metrics collector is started |
| `APP_KEY` | optional | reuse an existing key when rebuilding a VM; otherwise generated on first provision |
| `DB_CA_CERT` | optional | PEM of the provider's CA, for `sslmode=verify-full`; written to `/data/coolify/ssh/db-ca.pem` |

The pipeline loads everything under the prefix, so other parameters (R2 keys, GitHub App credentials, the email
token) can live there too; nothing reads them yet.

## The test gate

`scripts/prod/ci-tests.sh` runs every Feature and Unit test file in its own process (the upstream suite is
order-dependent and crashes in one process), four at a time, and retries a failing file once on its own.
`tests/avail-ci-skip.txt` lists what is skipped, always with a reason: tests that also fail on pristine
upstream `main`, and tests for behaviour Avail removed or changed. Upstream test files are never edited, so
syncs stay clean. After an upstream sync, run the workflow; a new failure is either a real regression or a new
line for the list.

## Scripts

| Script | Runs where | Does |
| --- | --- | --- |
| `ssm-load.sh` | the runner | reads every parameter under the prefix into a 0600 file; values are masked in the log |
| `ci-lib.sh` | the runner | `remote`, `remote_env`, `push_release` over Teleport. Secrets travel as a 0600 file on the VM that is deleted after use, never on a command line |
| `bootstrap-host.sh` | each VM | refuses to run unless the Teleport agent is running; key-only sshd on the Coolify port only (22 closed), `fail2ban`, `MaxStartups 30:60:200`, unattended upgrades, swap, Docker with 10m×3 log rotation. Control plane also: `/data/coolify` layout, the `coolify` network, Coolify's localhost key (made the only SSH key), and `.env` with `DATABASE_URL` (an existing `.env` and its `APP_KEY` are never overwritten) |
| `worker-key.php` | inside the `coolify` container | prints the public half of Coolify's app-server key `avail-workers`, creating it on the first run; the deploy step installs it on every app server |
| `localhost-public-key.php` | inside the `coolify` container | prints the public half of Coolify's "localhost's key" from the database; the deploy step makes it the control plane's only SSH key, so re-runs and a VM rebuilt from an existing database stay consistent |
| `localhost-proxy.php` | inside the `coolify` container | validates Coolify's own server and starts its proxy when it is not running (first-boot validation is never retried otherwise, and the dashboard stays down) |
| `ssh-authorized-keys.sh` | each VM | makes one public key the only key in `authorized_keys`: adds it, lists the others by fingerprint and, while Teleport is running, backs the file up and removes them |
| `deploy-release.sh` | control plane | checks the managed DB is reachable, records the previous image, pulls with a throw-away Docker config, runs `scripts/deploy-custom.sh <image>` |
| `deploy-platform.sh` | each VM | starts the Alloy shipper (`docker/avail-otel`: container logs, host and container metrics) with the SigNoz endpoint and the host name |
| `configure-instance.php` | inside the `coolify` container | auto-update off, sponsorship popup off, registration on, force HTTPS, instance URL, daily Docker cleanup, wildcard domain, SSH port of the local server, Clerk settings, Cloudflare ranges as Traefik trusted IPs. `DRY_RUN=1` shows changes without saving |
| `smoke-check.sh` | the runner | health, login page, HTTP→HTTPS, websocket 101, no password form |
| `notify-slack.sh` | the runner | posts the result to Slack; never fails the job |

`scripts/deploy-custom.sh` disables the bundled `postgres` service whenever `.env` has a `DATABASE_URL` (or a
`DB_HOST` other than `postgres`). The testing VM has neither, so it is unchanged.

## Not automated

- Everything in Cloudflare (setup step 6), buying Advanced Certificate Manager, WAF managed rulesets, restricting 80/443 to Cloudflare's ranges (provider firewall).
- Adding app servers in Coolify (Servers → Add), their proxy trusted IPs (re-run **deploy** after adding one) and their wildcard domain if it differs. Coolify's SSH key for them is made and installed by the pipeline.
- Custom app domains on the company zone, email, Coolify's notification channels (the Slack webhook is only used for deploy messages for now), S3/R2 backup storage, the restore drill, Clerk MFA and the break-glass test.
- SigNoz alerts and the dashboards for the log collector.

## Rollback

Run the workflow with **rollback** and the previous tag (the summary of every deploy prints it). Migrations are
not undone; use the provider's point-in-time restore if a migration has to be reverted.

## Assumptions behind this version

Where the production setup doc left a question open, this follows its stated default: `release.yml` replaces the
old build job and keeps deploy behind approval; `sslmode=require` until the provider's CA is known; both VMs are
enrolled in Teleport and a bot can be created; SSM prefix `/avail/coolify/prod/`; one Slack webhook; DigitalOcean
for VMs and registry. Two things the doc did not specify: a separate registry **push** token and a separate AWS
**build** role (see setup step 1), and Alloy (already in `docker/avail-otel`) as the log collector.
